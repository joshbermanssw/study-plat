## Summary

Week 7 covers elasticity and high availability on AWS — horizontal/vertical scaling, EC2 Auto Scaling, Elastic Load Balancing, and database scaling — turning static infrastructure into responsive cloud architectures.

- **Scalability vs elasticity**: elasticity adds fine-grained, automatic capacity expansion *and* contraction (cloud) on top of traditional scalability. Vertical = bigger instance; horizontal = more instances behind an LB.
- **EC2 Auto Scaling Group**: launch template + min/desired/max + multi-AZ distribution. Triggers via schedule, dynamic policies (target tracking on CPU, step), or predictive scaling. Integrates with ELB for registration and health.
- **CloudWatch**: metrics + alarms drive scaling actions and SNS notifications; alarms support static thresholds, anomaly detection, or metric math.
- **ELB types**: ALB (L7 HTTP/HTTPS, listener rules, target groups, round-robin or LOR), NLB (L4, ultra-low latency), Gateway LB (L3 appliance insertion), Classic (legacy). ALB health checks mark unhealthy targets; ASG can use ELB health checks to replace app-failed instances.
- **DB scaling**: RDS vertical push-button resize, up to 5 read replicas (async); Aurora supports 15 replicas sharing the cluster volume.

**Exam focus**: design an ASG + ALB + CloudWatch architecture for a bursty workload, and compare ALB vs NLB or Multi-AZ (HA) vs Read Replicas (scaling) for given requirements.
