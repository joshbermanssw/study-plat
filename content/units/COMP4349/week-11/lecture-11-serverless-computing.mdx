## Summary

Week 11 covers Function-as-a-Service / serverless on AWS — Lambda execution model, microVM isolation via Firecracker, and API Gateway as the HTTP front door — completing the IaaS -> containers -> serverless abstraction ladder.

- **FaaS principles**: decoupled compute and storage; stateless functions; pay only for execution time (ms-billed); provider manages provisioning. Trade control for operational simplicity.
- **AWS Lambda anatomy**: handler function + event object + context. Triggers: sync (API Gateway, Function URL) or async (S3, SNS, EventBridge schedule, SQS). Two permission planes — resource-based policy (who can invoke) vs execution role (what the function can do).
- **Execution environment**: each Lambda runs in a Firecracker microVM — stronger isolation than containers, lower overhead than full VMs — enabling safe multi-tenant scheduling. Ephemeral `/tmp` storage; Lambda layers share dependencies.
- **Anti-patterns**: Lambda monoliths, recursive S3-trigger loops, Lambda calling Lambda synchronously. Prefer many small functions, Step Functions for orchestration, SQS to decouple.
- **API Gateway**: managed REST/HTTP front end with throttling, auth, caching, multiple stages; routes requests to Lambda, EC2, or HTTP backends. Compare to ALB->EC2 (long-running, port-listening) vs APIGW->Lambda (per-invocation, function-based).

**Exam focus**: design a serverless image/data-processing flow (S3 -> Lambda -> DynamoDB) with correct invoke and execution-role permissions, and contrast serverless (Lambda) vs containerised (ECS) vs VM (EC2) compute on cost, scaling, and state.
